# 渲染架构

## 两个 DLL，一个单向依赖

| DLL | 内容 | 依赖 |
|---|---|---|
| `ConcordFlashGameEngineRuntime.dll` | `app`/`ecs`/`scene`/`window` | 仅 SDL3 |
| `ConcordFlashGameEngineRender.dll` | Vulkan 后端（`render/` 全部） | Runtime（取 `Window` 原生句柄）、SDL3、Vulkan |

这个划分复刻了第一代按模块拆 DLL 的思路（`CEngine.dll`/`CAudio.dll`/...），
但只拆成两个：渲染后端体量大、迭代快，值得独立；其余模块耦合紧密
（`Game` 同时拥有 `Window`、`Scene`、`SystemSchedule`），拆开反而增加
不必要的 DLL 边界。

### 打破循环依赖：自注册工厂 + 强制链接锚点

`Game::AttachWindow` 需要构造一个渲染后端，但 `Game` 所在的 Runtime.dll
绝不能 `#include` 具体的 `VulkanRenderBackend.h`——那会让 Runtime 反过来
依赖 Render，和 Render 依赖 Runtime 的方向冲突，形成循环。

解决办法是 `RenderBackendFactory`：

```cpp
// engine/render/RenderBackendFactory.h（Runtime.dll，只认识接口）
using CreateRenderBackendFn = std::unique_ptr<IRenderBackend> (*)();
void RegisterRenderBackend(CreateRenderBackendFn factory);
std::unique_ptr<IRenderBackend> CreateRenderBackend();
```

Render.dll 在自己的静态初始化阶段调用 `RegisterRenderBackend`——DLL 一旦被
加载，注册就在 `main()` 运行之前自动完成，应用代码不需要调用任何函数。

真正的难点是**让 Windows 先把 Render.dll 加载进来**。如果没有任何一处代码
引用 Render.dll 导出的符号，Windows 的隐式链接不会把它拉进导入表，静态
初始化器永远不会执行。`VulkanBackendRegistration.cpp` 因此额外导出一个
空函数作为链接锚点：

```cpp
extern "C" CRENDER_API void ConcordRenderBackendLinkAnchor() {}
```

`concord/CMakeLists.txt` 把强制解析这个符号的链接参数（GNU ld 用
`-Wl,-u,ConcordRenderBackendLinkAnchor`，MSVC 用 `/INCLUDE:...`）挂在
`concord::render` 的 `INTERFACE` 链接选项上，因此任何链接了
`concord::concord`（进而链接 `concord::render`）的目标都会自动拉入
Render.dll——**用户代码全程不出现渲染后端相关的任何符号**，`Game` 创建
和 `AttachWindow` 之后渲染就已经接好。

## Forward+ 路线图

目标管线：深度预通道 → 光源分块裁剪 → 前向着色。当前地基阶段完成的部分：

- ✅ 实例 / 物理设备选择（优先独显）/ 逻辑设备（启用 dynamic rendering）
- ✅ SDL 表面创建，与 Window 的唯一交汇点
- ✅ 交换链创建与按窗口尺寸变化重建
- ✅ 双缓冲帧同步（`MAX_FRAMES_IN_FLIGHT = 2`），每帧独立命令缓冲/信号量/栅栏
- ✅ dynamic rendering 清屏通道（按场景 `EnvironmentSettings::skyColor`）
- ✅ 初始化、swapchain 局部失败、最小化恢复和帧同步失败的回滚路径
- ✅ 可选 GLSL → SPIR-V 构建路径；无编译器时安全跳过，产物可 staging 到
  `Assets/Shaders/`
- ✅ 可选内置 Box 的 depth-only 预通道与基础 forward pass；缺少 shader 或 frame
  data UBO 时安全回退到清屏
- ✅ 光源分块裁剪第一版：固定 16×16 tile、128×128 最大网格、每 tile 最多 64
  个索引；compute pass 生成 light list，并通过 compute→fragment barrier 交给
  forward shader。点光/聚光使用保守屏幕包围裁剪，溢出或资源不可用时回退全灯遍历。
- [x] 方向光阴影首个可见切片：每个 frame slot 独立深度图、比较采样器和 descriptor
  set；固定焦点的 light view-projection、depth-only pass、forward set=1 采样和 3×3
  PCF 已接入；静态导入模型按 primitive 复用同一 depth pass 投射阴影。阴影资源或专用
  shader 不可用时自动回退无阴影 forward shader。
- [~] 前向着色管线骨架（Box 使用 96-byte per-object push constant，场景相机、
  环境光和最多 64 个方向/点/聚光灯记录来自 per-frame UBO；当前为简化
  Lambert + 高光模型，tile list 已接入但仍待深度分层/更精确裁剪）
- [~] 阴影贴图：当前为单方向光、固定 1024² map；级联/深度分层和自动截图回归待补。

### 可选硬件光线追踪

设备初始化会探测 `VK_KHR_acceleration_structure`、
`VK_KHR_ray_tracing_pipeline` 和 `VK_KHR_deferred_host_operations`，同时检查
buffer device address、加速结构和 RT pipeline feature，以及 shader binding table
对齐、最大 stride 和递归深度限制。全部条件满足时，logical device 自动启用这些
特性并记录 `VulkanContext::rayTracing`；若驱动还提供 `VK_KHR_ray_query`，则一并
启用对应 feature。任一驱动拒绝则只回退到原有 raster device，不影响 Forward+ 或
shadow map。`BuildVulkanRayTracingSbtLayout` 已提供溢出安全的 raygen / miss / hit
区域布局计算，`BuildVulkanRayTracingSbtRegions` 将已分配的 device address 转换为
`vkCmdTraceRaysKHR` 所需的区域描述。`VulkanRayTracingScene` 可选地创建程序化
unit Box 的 device-address 顶点/索引缓冲、BLAS、TLAS 和 scratch 资源；运行时用
`VulkanRayTracingSceneRing` 为每个 frame slot 保存独立副本，快照中的可见 Box 会
更新当前 slot 的实例缓冲。`RecordVulkanRayTracingSceneBuild` 负责在调用方的
command buffer 中录制输入可见性、BLAS → TLAS 顺序与必要 barrier，随后通过
`GL_EXT_ray_query` 的 set=2 前向变体查询遮挡；同时在完整 KHR 管线能力和内置
`raygen.rgen`、`raymiss.rmiss`、`rayhit.rchit` 产物可用时，Render DLL 会创建独立的
ray-generation/miss/closest-hit pipeline、SBT 和每帧 storage image，并将 primary-ray
结果合成到交换链。交换链 transfer destination、格式 blit 能力、扩展函数指针或
shader 产物缺失时安全回退现有 shadow-map/无阴影 raster 路径。应用代码不需要调用
连接 API，也不需要在 cx 示例中写 Vulkan。

## ConcordScript / C++ 扩展 Pass

`include/Concord/CRender.h` 是一个不传递 Vulkan 头文件的 opt-in facade。通过
`RegisterVulkanPass` 注册的回调会在 `BeforeScene` 或 `AfterScene` 阶段插入当前
frame 的引擎命令缓冲，也可以注册 `Initialize`/`Shutdown` 生命周期通知。回调收到
带 `version`、`structSize` 的 `VulkanPassContext`，设备、队列、交换链、深度、
descriptor 和本帧可用的 TLAS 以固定 64 位 opaque handle 提供；需要原生类型时，
扩展自己的翻译单元再包含 Vulkan SDK 并使用 `VulkanHandle<T>()` 转换。

生命周期阶段没有 acquired image：`imageIndex` 为
`VulkanPassInvalidImageIndex`，命令缓冲、附件、descriptor 和加速结构句柄均为零。
帧阶段的回调只能在引擎 command buffer 上追加记录，不能结束或提交它，也不能绕过
引擎修改 image layout 跟踪。回调返回 `false` 或抛出异常时只记录日志，其他 pass
仍继续执行；同一阶段按 `order` 再按注册顺序运行。

## 帧生命周期

```
Init(window, enableValidation)
  -> [ BeginFrame() -> DrawScene(scene) -> EndFrame() ] 重复
  -> Shutdown()
```

`BeginFrame` 负责：检测窗口尺寸变化并重建交换链、等待栅栏、获取下一张
可呈现图像、开启命令缓冲。零尺寸窗口会保留重建请求并在恢复后重试。
`DrawScene` 从 Scene 提取只读快照，将相机、环境和灯光打包并上传到当前 frame slot
的持久映射 UBO；frame-data 的 `IsReady()` 只表示 UBO、descriptor pool/set 可用，
`IsTileReady()` 另外表示每个 slot 都有完整 tile SSBO。完整 tile 资源可用时先
dispatch light-culling compute，再以 barrier 连接 Box 的深度预通道与 forward pass；
若完整 tile SSBO 分配失败，descriptor binding 1 会绑定一个最小占位 buffer，tile
flag 保持关闭，fragment shader 安全回退到全灯遍历。只有 UBO 或占位资源也无法
创建时才回退到清屏。Debug 校验层可用时，tile/depth/forward/clear 区段会
写入 command-buffer debug label。`EndFrame` 提交命令缓冲并
呈现，呈现结果为"过期/次优"时会重建交换链；录制或提交失败会重建该帧同步
对象，避免等待未 signal 的 fence。若阴影资源可用，DrawScene 会先为当前 frame slot
录制方向光 depth pass，再转换为只读布局供 forward set=1 的比较采样器使用；阴影
矩阵和启用位随 frame UBO 一起上传。每个 swapchain image 还记录当前占用的
frame fence，防止图像顺序与 frame slot 顺序不一致；重建时通过 `oldSwapchain`
交给驱动，候选资源成功后才替换旧对象。

摄像机投影的宽高比默认从当前 swapchain extent 自动计算；API 不要求调用方
手工同步窗口比例。固定比例只作为后续明确的可选覆盖项。

## 校验层

Debug 构建默认尝试启用 `VK_LAYER_KHRONOS_validation`；未安装时静默跳过
（`VulkanContext::validationEnabled` 记录实际结果，不会因为校验层缺失而
让初始化失败）。Release 构建里 `Game::AttachWindow` 强制关闭校验层。

## Vulkan 子模块划分

`render/vulkan/` 下每个文件对应帧生命周期的一个独立职责：

| 文件 | 职责 |
|---|---|
| `VulkanContext` | 贯穿始终的句柄集合（instance/device/queue/...） |
| `VulkanInstance` | 实例创建，请求 SDL 所需扩展和校验层 |
| `VulkanPhysicalDevice` | 队列族查找、物理设备优选 |
| `VulkanDevice` | 逻辑设备创建，启用 dynamic rendering 和可选 RT features |
| `VulkanSurface` | `SDL_Vulkan_CreateSurface`，SDL 与 Vulkan 的唯一交界 |
| `VulkanSurfaceFormat` | 表面格式与呈现模式选择 |
| `VulkanSwapchain` | 交换链、图像视图、per-image 信号量 |
| `VulkanDepthBuffer` | 每个 frame slot 的深度图像、view 和布局状态 |
| `VulkanFrameSync` | 命令池、per-frame 命令缓冲/信号量/栅栏及 recording 状态 |
| `VulkanFrameDataResources` | 每帧 host-visible UBO、可选完整 tile light-list SSBO（不可用时占位）、descriptor pool/set 和上传 |
| `VulkanBuffer` | 通用 Vulkan buffer 分配；可选持久映射、非 coherent flush/invalidate 和 buffer device address；`CreateVulkanHostBuffer` 保持旧调用兼容 |
| `VulkanImageBarrier` | 图像布局转换（undefined → 附件 → 呈现） |
| `VulkanClearPass` | dynamic rendering 清屏通道 |
| `VulkanBoxPipeline` | 可选 Box depth/forward pipeline 与两段动态渲染记录 |
| `VulkanTileLightCulling` | 可选 compute light-list 生成与 compute→fragment barrier |
| `VulkanShadowMap` | 可选、按 frame slot 隔离的可采样深度图、比较采样器、descriptor 和布局转换 |
| `VulkanShadowPipeline` | 方向光 depth-only dynamic-rendering 写入管线 |
| `VulkanShadowMath` | 稳定的单方向光选择、场景包围半径和 light view-projection 拟合 |
| `VulkanRayTracingSupport` | RT 扩展/feature/property 探测与安全能力快照 |
| `VulkanRayTracingPipeline` | SBT 区域对齐/溢出校验与 trace-region 描述构造 |
| `VulkanRayTracingScene` | 一个 frame slot 的可选 Box BLAS/TLAS 资源与 command recording |
| `VulkanRayTracingSceneRing` | 按 frame slot 隔离 RT 场景，避免并行帧写读竞争 |
| `VulkanPresent` | 提交队列与呈现 |
| `VulkanBackendRegistration` | 向 `RenderBackendFactory` 注册自己 |

`CreateVulkanBuffer` 接受 `VulkanBufferCreateInfo`：`persistentMap=false` 可用于
device-local 资源，`deviceAddress=true` 会自动补上
`VK_BUFFER_USAGE_SHADER_DEVICE_ADDRESS_BIT`，并通过
`VkMemoryAllocateFlagsInfo{VK_MEMORY_ALLOCATE_DEVICE_ADDRESS_BIT}` 分配和缓存地址。
旧的 `CreateVulkanHostBuffer` 仍然创建持久映射、host-visible buffer；`IsBound()`、
`IsMapped()` 和 `HasDeviceAddress()` 分别表达三种资源状态，避免把未映射的 RT
scratch/几何 buffer 误判为不可用。

每个文件不超过 150 行，只做一件事——这是仓库级别的硬约束（见 AGENTS.md）。

Tile light-list 的固定 ABI 为：每个 tile 一个 16-byte header（offset/count/overflow）
加 64 个 `uint` 索引；整个 SSBO 按 128×128 最大网格预分配，并按 frame slot 隔离。
compute pass 只做保守的屏幕包围测试，near-plane 相交光源会被纳入候选；当 tile
溢出、视口超过上限或可选资源缺失时，fragment shader 回退到完整 64-light 循环。
