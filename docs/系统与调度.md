# 系统与调度

系统是数据导向视图里的"行为"：与其让每个对象各自更新自己，不如让一个
系统批量遍历它关心的组件。

## 定义一个系统

```cpp
struct Spin { float degreesPerSecond = 45.0f; };

class SpinSystem final : public Concord::ISystem {
public:
    void OnUpdate(Concord::Scene& scene, Concord::f32 deltaTime) override
    {
        scene.Query<Spin, Concord::Transform>(
            [deltaTime](Concord::Entity, Spin& spin, Concord::Transform& transform) {
                transform.rotation.y += spin.degreesPerSecond * deltaTime;
            });
    }
};
```

`ISystem` 有三个可覆盖的钩子：

| 钩子 | 触发时机 |
|---|---|
| `OnStart` | 系统随场景第一次被 `Game::Run` 调度时，调用一次 |
| `OnUpdate` | 每帧调用一次，参数是场景和上一帧耗时（秒） |
| `OnStop` | 场景被替换或 `Game` 结束运行时，按注册的反序调用一次 |

## 注册

```cpp
game.Systems().Add<SpinSystem>();
```

`SystemSchedule::Add<T>` 构造并持有系统，按**注册顺序**执行——目前没有
依赖图，顺序就是唯一的调度依据。

## 只需要一个函数？

不必为一次性逻辑写一整个类：

```cpp
game.Systems().AddFunction("score-decay", [](Concord::Scene& scene, Concord::f32 dt) {
    // ...
});
```

`AddFunction` 内部把回调包进一个匿名 `ISystem` 实现，行为和写一个类完全
一致，只是省去样板代码。

## 和 `Game::OnUpdate` 的区别

`Game::OnUpdate` 是单个回调，替换式注册，适合应用层一次性的全局逻辑
（比如统计帧数、处理全局输入）。`SystemSchedule` 是可叠加的多系统列表，
适合把游戏逻辑拆成职责单一、可独立测试的单元。两者在帧循环里的顺序是
先 `OnUpdate` 回调，再 `SystemSchedule::Update`。
